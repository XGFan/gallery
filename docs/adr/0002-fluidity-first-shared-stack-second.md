# 媒体墙：流畅优先，共用技术栈次之

媒体墙是这个客户端 95% 的使用面，**它的流畅度就是 App 的流畅度**。因此优先级明确：

1. **滚动流畅是硬约束。**
2. iOS/macOS 共用一套实现是**偏好**，在硬约束面前让步。

起点是纯 SwiftUI（真正共用一套代码）。达不到性能门槛，就退回各平台独立实现
（`UICollectionView` / `NSCollectionView`），布局算法仍共享。

## 纯 SwiftUI 怎么写

不要用 `Layout` protocol。它是做瀑布流的直觉写法，但放进 `ScrollView` 后**不做视图回收**，
所有子视图都会被实例化，累积几千张图必然爆内存。

正确写法是：数据按"追加到最短列"分成 N 个数组，N 个 `LazyVStack` 并排塞进 `HStack`，
每列独立 lazy、独立回收。

代价：视觉顺序是"之字形"而非严格从左到右（瀑布流追加到最短列本来就打乱了严格顺序，
这个代价基本免费）；各列高度不同，滚到底时短列先见底。

最难的一处是**捏合改列数**——列数变化要重新分列，且必须保持当前滚动位置，否则手一捏
内容就跳走。这是这块代码里唯一需要仔细设计的地方。

## 切换判据

"撑不住再换"若没有判据就是空话。以下任一项在真机（iPhone 15 Pro Max，Development
签名的可调试构建）上不达标，即触发换实现：

- **帧率**：ProMotion 120Hz 下持续快速滚动，掉帧率 > 1%
- **内存**：累积滚动 2000 张图后常驻内存 > 500MB，或随滚动无界增长
- **捏合改列数**：重排出现可见跳动或掉帧

因此媒体墙必须从第一天起就**封在一个协议后面**，而不是让页面代码直接依赖 SwiftUI 的
分列细节——否则"换"就永远不会发生。这一层抽象是为兑现上面的优先级付的必要成本。

## Consequences

- macOS 端也要跑同一套判据。若只有 iOS 达不到，可以只在 iOS 换实现——共用是偏好，
  不是要求两端必须长得一样。
- 不要"顺手改成" `Layout` protocol 实现。那看起来更正统，但会退回到不回收视图的状态。

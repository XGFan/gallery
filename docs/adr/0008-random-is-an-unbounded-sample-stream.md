# random 是一条无限取样流，不是被打乱的序列

`random` 原本的实现是"把当前视图里的媒体打乱"——`MediaOrder.shuffled` 配一个可复现的
种子生成器，单测断言它确实是个排列。问题在于它打乱的是 `store.entries`，也就是**已经翻
到的那几页**。在 `image` 视图里刚进一个文件夹只加载了 150 条，这时按 `random`，随机就
只在这 150 条里打转；而这 150 条按路径排序，基本全来自同一个相册。

对齐 Web 的做法是一次拉全量再打乱（`/api/image/` 无 limit）。根目录 100,517 件媒体、约
20MB JSON，按下到出图会有可见的等待。

## 决定

改用 `/api/random/`，加两个参数：

```
GET /api/random/{path}?flat=true&type=image|video|all&count=N
```

`type` 默认 `image`（保持现有语义），客户端按「混合/隔离」偏好传 `all` 或 `image`——这个
偏好因此从客户端本地设置变成了一个请求参数。客户端一次要 30 条，划到剩 10 条时要下一批。

`/api/random/` 此前**没有任何调用者**（Web 的 `random` 走的是 `/api/image/`，见
`App.tsx` 的 `requestMode` 映射；tiny-viewer 也不用），所以接口形状可以自由改。

**分布不均匀不修。** `Random()` 在每一层的 Images 与 Directories 之间按个数均分概率，
一个装 1 张图、另有一个 5000 张子树的目录，那 1 张图会拿到一半的概率。这是取样的实现
方式，不是要修的缺陷。

要和它区分开的是另一件事：选子目录的循环原本缺 `break`，`restIndex` 归零后会被后续
每个目录覆盖，实际总是下钻到 map 恰好最后吐出的那个子目录——那不是"偏斜的取样"，
是取样根本没按自己的规则跑。`break` 已补上（`core/types.go`）。偏斜保留，失效不保留。

## Consequences

- **播放器必须能处理无界序列**：没有总数，没有"看完一轮"，同一件媒体可能再次出现。
  `ViewerView` 的 `位置 / 总数` 计数器失去分母，只显示序号。
- `MediaOrder` 整块下线——`shuffled`、`SeededGenerator`、`sequence` 的混合/隔离逻辑，
  以及 `ViewerLogicTests` 里对应的那批单测。它们唯一的调用者就是旧的 `random`。
- 取样在后端做，客户端内存与文件夹大小无关：10 万件和 100 件的开销一样。
- 想换成"可证明是排列"的真·全局随机，路是清楚的：给 `/api/media/` 加
  `?shuffle=<seed>` 让后端对固定种子给出稳定排列。这条路当时被否掉是因为它要动后端的
  查询语义，而无限流零后端改动（只加参数）就够用。

# 图片只用现有的 1920px 一档，多尺寸缩略图暂缓

客户端当前的使用场景都在局域网内，带宽不是瓶颈。因此不为它新增后端缩略图档位，
**网格与全屏共用现有的 `/thumbnail/`（长边 1920px）**，捏合放大后才回源 `/file/` 原图。
后端零改动。

## 为什么不是直接用原图

局域网解决了带宽，没解决解码开销。库里 2560×3838 的图解码成 bitmap 约 29MB，一屏
20 张接近 590MB——这与 ADR-0002 定下的"内存 500MB"硬约束直接冲突。1920px 那档解码后
约 9.8MB，配合 Kingfisher 的 `DownsamplingImageProcessor` 在解码期降到显示尺寸，内存可控。

## 副产品

网格与全屏共用同一档 ⇒ 从网格点进全屏是缓存命中，秒开。这与 Web 前端"网格直接加载
原图、点开灯箱时浏览器缓存命中"是同一个取舍，只是把档位从原图换成了 1920px。

## 什么时候该做 512px 档

这个决定的前提是"局域网"，而 App 装在手机上，出门就在蜂窝网——前提是有有效期的。
触发条件任一满足即应补上 ~512px 档并让网格改用它：

- 蜂窝网下滚动媒体墙出现明显的图片填充延迟
- 真机上媒体墙触碰 ADR-0002 的性能判据，且定位到瓶颈在图片解码

届时的代价是一次性为约 98k 张图生成缩略图，磁盘约 +3GB。

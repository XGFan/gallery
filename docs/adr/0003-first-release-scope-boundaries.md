# 原生客户端第一期明确不做的三件事

新的 iOS/macOS 客户端的目标是"把 Web 已有的能力原生化"，而不是做一个功能超集。
以下三项在讨论中被逐一提出并**明确排除**，记录在此以免半年后重新讨论一遍。

## 一、标签与说明（tag / caption）

后端已经具备完整的 AI 标注能力并已产出数据：`.cache/.img-tag.json` 含 **96,667 张图**
的标签（46MB），`.cache/.img-caption.json` 含 **5,373 条**说明，`/api/tag` 提供全局标签
统计，配置里有 `TagBlacklist`，README 也把"AI 增强"列为核心特性。

**但现有 Web 前端一行都没用过它**（`grep -rni "tag|caption" web/src` 零命中，`/api/tag`
无任何调用者）。既然本期以对齐 Web 能力为准，客户端同样不使用。因此这次的后端改造
只做分页，**不做成带筛选的查询接口**。（后来 `/api/random/` 加了 `type` 与 `count`
两个参数，那不是筛选接口，是取样接口——见 ADR-0008。）

代价是清楚的：一个 98,762 张图的库，纯靠文件夹逐层翻找的效率很差，而能解决这件事的
数据其实已经躺在磁盘上了。真要做时，后端需要再改一次并建标签倒排索引。

## 二、离线主动下载

"出门前把一个文件夹下下来" 是原生客户端相对 Web 的天然优势，但它不在 Web 能力范围内，
与本期目标不符。图片的**透明磁盘缓存**照做——那是 Kingfisher 自带的，不算新增范围。

## 三、访问鉴权

不实现。并非因为后端没有鉴权——恰恰相反，Gallery 一直挂在 homelab 的 tinyauth 之后
（Traefik forwardAuth → tinyauth → Pocket ID passkey），只是对内网网段配了 IP bypass，
而客户端的使用场景正在这些网段内。详见 ADR-0004。

客户端因此只需要一个 baseURL：没有登录流程、没有凭证存储、没有会话过期处理。

> 这顺带避开了超级签证书**共享 Keychain** 的问题——同证书签的所有 App（包括"全能签"
> 这类来路不明的工具）能读到彼此的 Keychain 条目，所以在这个签名体系下用 Keychain 存
> 任何凭证等于不存。见 `ios-cert/README.md`。
